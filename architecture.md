# architecture.md

## What this is

**Vigil** — a citation-backed exchange/securities-market regulatory reporting and surveillance copilot, built on Snowflake's Cortex/CoCo stack. Full pivot from a prior banking-credit-risk prototype (`Praman`, a sibling hackathon repo) to a different regulatory domain: **exchange market conduct, position/exposure limits, post-trade transaction reporting, and best execution** — not bank Basel/Pillar-3 reporting. Same Snowflake account as `Praman`, disjoint schema (`VIGIL.CORE` / `VIGIL.EVAL`), no shared objects.

**Design mandate, different from how `Praman` was built:** market-agnostic from the first line of DDL, not retrofitted after a single-market prototype. `Praman`'s own `plug_and_play_architecture.md` found that jurisdiction-agnostic design bolted on afterward still left real gaps (hardcoded currency, hardcoded thresholds, an implicit assumption the schema never needs to change). This project applies those findings as day-one constraints instead of after-the-fact fixes — see "Market-agnostic design rules" below, and note in each section where a rule exists specifically because of a documented `Praman` mistake.

## Scope: four obligation types, one canonical schema

1. **Trade surveillance / market conduct** — wash trading, spoofing/layering, abnormal volume/price patterns.
2. **Position/exposure limits** — concentration of a position in an instrument vs. a regulatory threshold.
3. **Post-trade transaction reporting** — timeliness, completeness, and accuracy of trade reports submitted to a regulator/exchange.
4. **Best execution / order reporting** — execution price vs. a reference price, order-routing quality.

These share one schema and one detector framework the same way `Praman`'s four stages shared one banking schema — the four obligation types are different *queries* over the same core entities (orders, trades, positions, submitted reports), not four independent data models.

## Data model

**One regulator oversees many venues — verified live, not assumed.** Fetching JPX's own site, Japannext PTS's own site, and Osaka Digital Exchange's own site confirmed Japan alone has at least 5 real active trading venues (TSE, OSE, TOCOM as the JPX Group exchanges, plus Japannext PTS and ODX operating outside it — ODX's own site describes itself as "the third PTS in Japan"), all under one regulator (FSA/SESC). Two further venues, Cboe Japan's PTS and the Cboe BIDS Japan block trading platform, are **primary-source confirmed discontinued** — Cboe Global Markets' own July 23, 2025 investor-relations press release announced winding both down, with operations expected to suspend August 29, 2025 — retrieved via Wayback Machine after the live IR page returned an HTTP 403 to a direct fetch. Both are seeded, not excluded: real historical trades exist before that closure date and must stay representable, which is why `VENUES` carries actual date bounds (below), not just a status flag. The US shows the identical one-regulator/many-venues shape at larger scale: the SEC directly oversees 24+ separate national securities exchanges plus FINRA, and — re-confirmed live this session via the CAT NMS Plan's own site — SEC Rule 613 legally requires all of them to feed one Consolidated Audit Trail specifically so the regulator can surveil across venues. This is why the schema below has a `JURISDICTION_ID` (the regulator, owning obligations/rules/calibration) and a separate `VENUE_ID` (the specific exchange/PTS a trade executed on) rather than one collapsed `MARKET_ID` — full rationale, the verified Japan venue list, and structural-review revisions (v3, v4, v5, v6, v7) are in `docs/canonical_schema_contract.md`, the authoritative column-level reference; this section is a summary.

**A structural review of the first schema draft found nine real gaps** — a detector exemption that quietly reintroduced a hardcoded threshold, a wash-trading detector that could go silently blind, a `POSITIONS` diagram that contradicted its own derivation rule, a best-execution formula that was outright wrong (not just deferred), a governance gate enforced by policy instead of structure, a missing write path for the actual market data, and two undefined identifier spaces. All nine are fixed in `docs/canonical_schema_contract.md` v3, marked `[FIX #1]`–`[FIX #9]` there; this section reflects the fixed state, not the original draft.

**A second review — a milestoning audit — found that "append-only" was true in name only.** Only `POSITIONS` and `DETECTOR_CALIBRATION` actually satisfied it; every other table either had no versioning, or the doc itself required an in-place `UPDATE` with no append-only path defined (`OBLIGATION_MAP`'s proposed→approved flip, `ORDERS`' mutable lifecycle fields, `TRANSACTION_REPORTS`' submission fields). Fixed in `docs/canonical_schema_contract.md` v5 (`[FIX #10]`–`[FIX #19]`) with one universal, plug-and-play rule instead of nine bespoke ones — see "Milestoning rules" below.

**A third review — of two market-structure cases the first draft never tested against, internal cross trades and how a report actually gets generated — found two more real gaps.** Nothing distinguished a legitimate internal/agency cross from a wash trade, since both match the same detector pattern (same beneficial owner, matched buy/sell, within tolerance). And separately, the schema could check whether a report was submitted on time and matched its trade, but never modeled what a regulator's own circular actually requires it to *contain* — a fixed field list that changes when the regulator amends it. Fixed in `docs/canonical_schema_contract.md` v6 (`[FIX #20]`–`[FIX #26]`): `TRADES.MATCHING_MECHANISM` for the first, and a new `REPORT_TEMPLATES`/`REPORT_TEMPLATE_RULE_CHUNKS` pair (mirroring `OBLIGATION_MAP`/`OBLIGATION_RULE_CHUNKS`) for the second.

**A follow-up question — what happens when a circular requires a field the schema has no source for at all — found v6 had described a governance check without ever giving `REPORT_TEMPLATES` the `STATUS` lifecycle that check depends on.** Fixed in v7 (`[FIX #27]`–`[FIX #29]`): `REPORT_TEMPLATES` gains `STATUS` (`proposed`/`mapped`/`gap`); `gap` is a deliberate, non-blocking state for a required field with no current data source, surfaced via a new `REPORT_TEMPLATE_COVERAGE` view rather than silently dropped, fabricated, or left to block the whole template.

**An external code review found `REPORT_TEMPLATES`' actual content hadn't kept pace with its own schema, plus a real RBAC asymmetry.** `REPORT_TEMPLATES` had exactly 4 fields (JP `transaction_report`) against what a real transaction-reporting regime actually requires — MiFIR RTS 22 (Commission Delegated Regulation (EU) 2017/590) specifies 65 — and `GOVERNANCE_WRITE` could `INSERT` into `REPORT_TEMPLATES`/`REPORT_TEMPLATE_RULE_CHUNKS` but never `SELECT` them back, unlike its existing `OBLIGATION_MAP` grant (Fix #6). Fixed 2026-09-15: **`[FIX #30]`** — `GOVERNANCE_WRITE` gains `SELECT` on `REPORT_TEMPLATES`/`REPORT_TEMPLATE_RULE_CHUNKS` and their `_CURRENT` views (`sql/rbac/03_governance_write.sql`). Separately (not a schema fix, a content + adaptor fix): all 65 real RTS 22 Annex I Table 2 fields, extracted and verified via `pdftotext` against a primary-source PDF, were seeded under `JURISDICTION_ID='EU'` — RTS 22 is the EU's own standard, so seeding it under `JP` would misattribute a European rule to Japan's still-unsourced format (`sql/governance/03_eu_report_template_rts22_seed.sql`); 7 of 65 honestly resolve to a real `TRADES` column, the other 58 (LEI/natural-person fields, every derivative/option field, waiver/short-sale/OTC indicators) are `gap`. And the report-generation adaptor `[FIX #25]` names as unbuilt now has a first, narrow, real implementation — `SP_RENDER_REPORT_PAYLOAD` (`sql/procedures/sp_render_report_payload.sql`) renders an actual CSV from whichever fields `REPORT_TEMPLATES_CURRENT` says are genuinely `mapped`, re-validates every mapping against live `INFORMATION_SCHEMA` before touching dynamic SQL, and writes a real `REPORT_PAYLOAD_REF` — verified end to end against a live JP trade, not just "the call returned OK." It is not the regulator's actual XML/fixed-width submission format; see the "Build order" section below for what that would still take.

Full diagram set (system architecture, milestoning mechanism, ingestion/detection sequence, governance-gate sequence, per-role user flows, RBAC matrix) is in `docs/system_diagrams.md` — this ASCII sketch stays a summary, not the source of truth for the shape.

- **`JURISDICTIONS`** — one row per regulator (`JURISDICTION_ID`, `REGULATOR_NAME`, `PRIMARY_LANGUAGE`).
- **`VENUES`** — one row per exchange/PTS/OTC/block-trading facility (`VENUE_ID`, `JURISDICTION_ID`, `VENUE_TYPE`, `OPERATOR_NAME`, `STATUS` — `active`/`discontinued` — plus `ACTIVE_FROM`/`DISCONTINUED_AT` dates). The dates exist because `STATUS` alone can't support a closed venue's real historical trades (Cboe Japan's PTS above is the concrete case) — a generator/adaptor stops producing *new* trades for a venue past its `DISCONTINUED_AT`, but existing historical trades before that date stay fully representable. A `STATUS` transition is a new row keyed by `LOADED_AT` (Fix #10), never an `UPDATE` — v3/v4 left this table with no legal way to record that transition at all.
- **`BENEFICIAL_OWNERS`** — new reference table (Fix #8). A beneficial owner is not assumed to be a market participant itself; `MARKET_PARTICIPANTS.BENEFICIAL_OWNER_ID` FKs here, not self-referencing `PARTICIPANT_ID`.
- **`INSTRUMENTS`** — reference data, scoped by `JURISDICTION_ID` (an instrument's primary-listing jurisdiction), not by venue — the same TSE-listed stock also trades on Japannext PTS under one instrument identity.
- **`MARKET_PARTICIPANTS`** — brokers/members/counterparties, scoped by `JURISDICTION_ID`. `BENEFICIAL_OWNER_ID` nullable, FK → `BENEFICIAL_OWNERS` when populated — needed for wash-trading detection across nominee accounts.
- **`ORDERS`** — **event-sourced (Fix #16)**: one row per order event (`new`/`modify`/`partial_fill`/`fill`/`cancel`, each with its own `EVENT_TS`), not one mutable row per order — the pre-v5 schema's `MODIFIED_TS`/`CANCELLED_TS` fields on a single row implied in-place mutation with no role ever granted it. Carries `VENUE_ID`/`JURISDICTION_ID`/`CURRENCY`, and `REGULATORY_ATTRIBUTES VARIANT` (Fix #26) for jurisdiction-specific regulatory fields no detector reads. Cancelled-but-unfilled orders (read from `ORDERS_CURRENT`) are the raw material for spoofing/layering detection. **Never a source for `POSITIONS`** (Fix #4) — an order is not itself an economic position.
- **`TRADES`** — executed trades, carrying `VENUE_ID`/`CURRENCY`. The sole source for `POSITIONS` accumulation. `ORDER_ID` and `COUNTERPARTY_PARTICIPANT_ID` are both independently nullable — when both are null on the same row, that trade is invisible to wash-trading detection, surfaced (not hidden) by `WASH_DETECTION_COVERAGE` below (Fix #3). Immutable once printed — a bust/amendment is a row in the new companion table `TRADE_CORRECTIONS` (Fix #15), never a mutation of the print itself. Carries `MATCHING_MECHANISM` (`continuous`/`cross`/`block`/`auction`, Fix #20) so a legitimate, disclosed internal cross can be told apart from a wash trade, and `REGULATORY_ATTRIBUTES VARIANT` (Fix #26) for jurisdiction-specific regulatory fields (LEI, trading capacity, short-sell flag) no detector reads.
- **`TRADE_REFERENCE_PRICES`** — new (Fix #5). `REFERENCE_PRICE_AT_EXECUTION` and `REFERENCE_PRICE_AT_ARRIVAL`, externally sourced by its own adaptor, kept off `TRADES` since reference prices arrive on their own timeline.
- **`POSITIONS`** — per `PARTICIPANT_ID` x `INSTRUMENT_ID` x `JURISDICTION_ID` x `AS_OF_DATE` x `LOADED_AT`, `NET_QUANTITY` (cumulative signed sum of `TRADES.VOLUME`, never `ORDERS`), `MARKET_VALUE`, `CURRENCY`. **No `VENUE_ID`** — a concentration/exposure limit is a cross-venue total. `LOADED_AT` (Fix #4) means a restatement is a new row, never an `UPDATE` — same append-only discipline as `Praman.AUDIT_LOG`. Corporate-actions adjustment is explicitly deferred, not silently ignored.
- **`TRANSACTION_REPORTS`** — the actual submission record, milestoned (Fix #14): created/submitted/matched are each a new row keyed by `LOADED_AT`, not in-place updates to `SUBMITTED_AT`/`FIELDS_COMPLETE`. `MATCH_STATUS` is now a defined enum (`full_match`/`partial_match`/`no_match`, Fix #9) against `TRADES`' instrument/price(exact)/volume(exact)/execution-timestamp(documented tolerance). `TRADE_ID` is nullable with a `REPORT_SCOPE` (`trade`/`periodic`/`nil`, Fix #23) so periodic/nil filings not tied to one trade are representable; `REPORT_STATUS` (`new`/`amendment`/`cancellation`, Fix #24) distinguishes an internal correction from an actual outbound message to the regulator; `REPORT_PAYLOAD_REF` (Fix #25) records what was actually submitted — populated for real by `SP_RENDER_REPORT_PAYLOAD` (see the external-review paragraph above), not permanently `NULL`; `DEFERRED_PUBLICATION_UNTIL` (Fix #26) covers a large-in-scale block trade's permitted delayed public disclosure, kept distinct from the submission `DEADLINE`.
- **`REPORT_TEMPLATES`** — new (Fix #21). What a regulator's own circular actually requires a report to contain — field-by-field, per (`JURISDICTION_ID`, `REPORT_TYPE`) — modeled for the first time; previously `TRANSACTION_REPORTS` could check timeliness and trade-match but not conformance to an actual required format. Milestoned like everything else, so a historical submission stays checkable against the template version in force when it was submitted. Carries its own `STATUS` (`proposed`/`mapped`/`gap`, Fix #27) — `gap` is the deliberate, non-blocking answer for a required field the schema has no current source for, surfaced by `REPORT_TEMPLATE_COVERAGE` (Fix #28) rather than silently dropped or fabricated. `FIELDS_COMPLETE` (Fix #22, #29) is computed against this table's `IS_REQUIRED AND STATUS = 'mapped'` fields, not `gap` ones, so a structural gap surfaces once as a template-level finding instead of making every report of that type permanently incomplete. `REPORT_TEMPLATE_RULE_CHUNKS` mirrors `OBLIGATION_RULE_CHUNKS` — every required field is traceable to the circular paragraph that mandates it. Live content: JP `transaction_report` has 4 fields (all `mapped`, generator-internal names); EU `transaction_report` has the real 65-field RTS 22 Annex I Table 2 list (7 `mapped`, 58 honestly `gap`) — see the external-review paragraph above for why EU, not JP.
- **`OBLIGATION_MAP`** — the `LINE_ITEM_MAP` equivalent, scoped by `JURISDICTION_ID`. `RULE_CHUNK_ID` moved out to a new `OBLIGATION_RULE_CHUNKS` junction table (Fix #9 — an obligation can be backed by zero, one, or many rule chunks, and now removable via an `IS_ACTIVE` tombstone row rather than `DELETE`, Fix #13). `SOURCE_TABLE`/`SOURCE_COLUMNS` stay free text (SQL can't enforce an FK to a dynamic column name) but must pass a schema-existence check before `GOVERNANCE_WRITE` can approve the row. The proposed→approved flip is itself a new row, not an `UPDATE` (Fix #12) — `GOVERNANCE_WRITE`'s grant on this table is `INSERT`-only.
- **`APPROVED_OBLIGATIONS`** — new view (Fix #6), the latest `LOADED_AT` row per obligation `WHERE STATUS = 'approved'` (redefined per Fix #12 to read against the milestoned table). The only obligation-lookup target the agent/`ANALYST_READ` are granted — the governance gate is now structural, not a rule every future query author has to remember to apply.
- **`RULE_CORPUS`** — same shape as `Praman`'s, scoped by `JURISDICTION_ID`, `SOURCE_AUTHORITY`/`ORIGINAL_LANGUAGE` from day one — directly relevant here since Japan's FSA/SESC's authoritative text is Japanese. Milestoned (Fix #17): a rule amendment is a new row, so a past citation stays reproducible against the text actually shown at the time.
- **`AUDIT_LOG`** — append-only by grant, same as `Praman`.

**Every table above also carries `CREATED_AT`/`CREATED_BY`/`LOADED_AT`/`LOADED_BY` and a generic `_CURRENT` view (Fix #19) — see "Milestoning rules" below.** This is a schema-wide convention, not a per-table callout, so it isn't repeated in every bullet above; `docs/canonical_schema_contract.md` v5 has the full column-level detail for each table.
- **`DETECTOR_CALIBRATION`** — append-only, effective-dated, `JURISDICTION_ID` required, `VENUE_ID` nullable, `IS_PROVISIONAL` cold-start flag, plus a new `PARAMS VARIANT` column (Fix #2) so pattern-match detectors (wash trading's time window/price tolerance) also read their tunables from this table — no detector, statistical or not, embeds a literal. Retrofitted with `CALIBRATED_BY`/`CREATED_AT`/`CREATED_BY` (Fix #19) — it had timestamp-based milestoning from day one but, like every other table, no record of who performed a recalibration.

## Market-agnostic design rules (day-one constraints, not later fixes)

Each rule below exists because a specific `Praman` gap is documented as a fix-later item in `plug_and_play_architecture_v2.md` — applying it here up front instead of waiting to hit the same problem twice.

1. **No hardcoded currency, venue, or jurisdiction anywhere.** `CURRENCY`, `JURISDICTION_ID`, and `VENUE_ID` are non-nullable (where applicable), non-defaulted columns from the first DDL — `Praman`'s `DEFAULT 'INR'` was flagged as a "cheap fix" needed later; here there's no default to begin with.
2. **Every detector baseline partitions by `JURISDICTION_ID` and/or `VENUE_ID` (whichever the obligation is actually scoped to) and `CURRENCY` where relevant, in addition to instrument/participant.** A cross-jurisdiction, cross-venue, or cross-currency aggregate is never computed implicitly inside a detector view — `Praman`'s currency/FX gap (summing unlike currencies into one baseline) is avoided by construction, not patched after the views exist. Which scope is correct differs by detector (see "Detectors" below): spoofing/layering is venue-scoped, concentration limits are jurisdiction-scoped only — getting this wrong in either direction is a real modeling error, not a style choice.
3. **No hardcoded detector parameters — statistical or pattern-match.** Every detector reads its tunables from `DETECTOR_CALIBRATION`: `Z_THRESHOLD`/`MIN_BASELINE_PERIODS` for statistical detectors, `PARAMS` (a `VARIANT` column) for pattern-match/rules-based ones. This closed a real gap in the first draft — wash trading's "pattern-match, not a z-score detector" framing had quietly left its time-window and price-tolerance values with no stated home, which was the same hardcoded-threshold problem rule #3 exists to prevent, just relabeled. `Praman` hardcoded `|z| >= 3` and only planned to calibrate it afterward; here `DETECTOR_CALIBRATION` exists before the first detector view does, with a documented cold-start default (`IS_PROVISIONAL = TRUE`) for a jurisdiction/venue/participant with insufficient history.
4. **The canonical schema is versioned and documented as a contract before a second jurisdiction is onboarded**, not consolidated from scattered DDL comments after the fact. `docs/canonical_schema_contract.md` is written alongside the DDL, not after it — and has already been revised four times (v1→v2 after live-verifying Japan's venue structure; v2→v3 after a structural review found nine gaps; v3→v4 for venue date-bounding; v4→v5 after a milestoning audit), all before any DDL existed to make those revisions expensive.
5. **Jurisdiction-specific dimensions are added as nullable extension columns, never by forking the schema per jurisdiction.** If a jurisdiction's regulator requires a dimension no other jurisdiction needs (e.g., a specific participant classification), it's a nullable column, following the same convention `Praman`'s plug-and-play doc settled on for banking (Fix #2) — applied here as the starting convention rather than a later resolution to a contradiction.
6. **`RULE_CORPUS` carries `SOURCE_AUTHORITY`/`ORIGINAL_LANGUAGE` from the first row loaded**, so a non-English-original jurisdiction's content is never treated as equivalent to the authoritative text without an explicit flag saying so — directly applicable to the first real jurisdiction below (Japan).
7. **Detector thresholds and obligation mappings are per-`JURISDICTION_ID` (and per-`VENUE_ID` where the detector is venue-scoped), never global constants** — `DETECTOR_CALIBRATION` and `OBLIGATION_MAP` are keyed this way, so onboarding jurisdiction #2 is a new set of rows, not a schema or SQL change.

## Milestoning rules (day-one constraint, not a later fix)

**Nothing in `VIGIL.CORE` is ever deleted or mutated. Every state change, correction, or removal is a new, dated row.** Applied as one plug-and-play convention, the same way the market-agnostic rules above are — onboarding a new table means adding one column set and one view from a fixed template, never inventing a bespoke versioning scheme per table. Full column-level detail (including which tables needed a structural redesign, like `ORDERS` becoming event-sourced) is in `docs/canonical_schema_contract.md` v5, `[FIX #10]`–`[FIX #19]`; the rule itself:

1. **Every table carries four audit columns: `CREATED_AT`/`CREATED_BY` and `LOADED_AT`/`LOADED_BY`.** `LOADED_AT`/`LOADED_BY` record when and by whom *this specific row* was written; `CREATED_AT`/`CREATED_BY` record when and by whom the *underlying entity* was first created, carried forward unchanged across every later milestoned version of the same natural key — so "when was this created" stays answerable without walking back through every correction.
2. **`LOADED_AT` (or an equivalent natural event timestamp) is part of every table's primary key**, so multiple versions of the same entity coexist as distinct rows instead of colliding.
3. **No functional role is ever granted `UPDATE` or `DELETE` on any `VIGIL.CORE` table — full stop.** Not an enumerated list of append-only tables with everything else implicitly exempt (that gap is exactly how `OBLIGATION_MAP` ended up with an `UPDATE` grant before this fix) — a blanket rule enforced by the grant scripts in `sql/rbac/` themselves never issuing `UPDATE`/`DELETE`.
4. **A "removal" is a tombstone row** (e.g. `OBLIGATION_RULE_CHUNKS.IS_ACTIVE = FALSE` with a later `LOADED_AT`), never a `DELETE`.
5. **Every table gets one generic `<TABLE>_CURRENT` view** — latest `LOADED_AT` per natural key via `QUALIFY ROW_NUMBER() OVER (PARTITION BY <key> ORDER BY LOADED_AT DESC) = 1` — the one piece of SQL every table reuses verbatim.

Two tables (`POSITIONS`, `DETECTOR_CALIBRATION`) already followed this pattern before it was formalized; everywhere else it's new as of this pass, including one real structural change — `ORDERS` moves from one mutable row per order to one row per order *event*, since its `MODIFIED_TS`/`CANCELLED_TS`/in-place `FILLED_QUANTITY` fields assumed a mutation path the RBAC design never actually granted anyone.

## Detectors — one framework, four obligation types

Reusing `Praman`'s "one detector formula, multiple consuming views" pattern (`ZSCORE` UDF), extended with new formulas the banking domain never needed:

- **Wash trading** (market conduct) — a `TRADES` row where the participant on both sides resolves to the same `BENEFICIAL_OWNER_ID`, or a matched buy/sell pair in the same instrument within a time window and price tolerance **read from `DETECTOR_CALIBRATION.PARAMS`** (Fix #2 — not hardcoded, despite being a pattern-match rather than statistical detector). Scoped per `VENUE_ID` but must also check *across* venues for the same instrument/beneficial owner — a pattern spread across TSE and Japannext to avoid one venue's detection is itself the case to catch. **A matched pair is not automatically a wash trade** (Fix #20) — `TRADES.MATCHING_MECHANISM` records whether the match was `continuous`/`cross`/`block`/`auction`, and which mechanisms are exempt from the pattern-match trigger (and under what disclosure condition) is itself read from `DETECTOR_CALIBRATION.PARAMS`, not hardcoded — a jurisdiction where a disclosed internal cross needs no special marking and one where it does both configure this without a schema change. Exemption from the trigger is not exemption from review: a `cross` trade still counts in `WASH_DETECTION_COVERAGE` and can still be a legitimate finding if mispriced. **Companion requirement, not optional:** `WASH_DETECTION_COVERAGE` (Fix #3) surfaces, per venue/day, the percentage of trades with neither a resolvable `ORDER_ID` nor a disclosed `COUNTERPARTY_PARTICIPANT_ID` — any wash-trading finding is presented alongside this coverage figure, so "no wash trades found" and "no wash trades could be checked for" are never conflated.
- **Spoofing/layering** (market conduct) — per participant x instrument x venue x day, ratio of cancelled-unfilled order volume to submitted order volume, z-scored against that participant's own trailing baseline **at that venue** (same `ZSCORE` UDF, reused formula) — a structurally identical computation to `Praman.TRANSACTION_SIGNALS`' structuring detector, applied to `ORDERS` instead of `TRANSACTIONS`. Venue-scoped in `DETECTOR_CALIBRATION` because order-book cancel-rate norms genuinely differ by venue (e.g. Japannext's separate Night Market session has its own liquidity profile).
- **Position/exposure limit breach** — `POSITIONS.NET_QUANTITY` (or market value) as a percentage of a regulatory threshold per instrument/participant class, scoped by `JURISDICTION_ID` **only** — structurally identical to `Praman`'s counterparty concentration check on `POSITIONS`, and consistent with `POSITIONS` itself having no `VENUE_ID` (the limit is on a cross-venue total accumulated from `TRADES` only — never `ORDERS`, Fix #4).
- **Post-trade reporting timeliness/completeness** — `TRANSACTION_REPORTS.SUBMITTED_AT` vs. `DEADLINE` (a boolean/interval, not a z-score) and `FIELDS_COMPLETE` (a required-field-presence check **against `REPORT_TEMPLATES_CURRENT WHERE IS_REQUIRED AND STATUS = 'mapped'`**, Fix #22/#29 — not an unspecified black box, and not measured against a `gap` field it could never satisfy) — a rules-based detector, not statistical, since lateness has a hard deadline rather than a distribution. `MATCH_STATUS` is a defined enum (Fix #9), not an unspecified "matches or not," and is `NULL` for a `periodic`/`nil`-scoped report (Fix #23) with no trade to match against. `REPORT_TEMPLATE_COVERAGE` (Fix #28) is the companion figure for this detector, same role `WASH_DETECTION_COVERAGE` plays for wash trading — surfacing which required fields the schema can't currently source at all. Scoped by `JURISDICTION_ID` + the report's `VENUE_ID` where the reporting facility itself is venue-specific.
- **Best execution — two distinct metrics, not one conflated formula (Fix #5).** `EXECUTION_SLIPPAGE`: `TRADES.PRICE` vs. `TRADE_REFERENCE_PRICES.REFERENCE_PRICE_AT_EXECUTION` (at `EXECUTION_TIMESTAMP`) — was the fill fair given the market at that instant. `ARRIVAL_SLIPPAGE`: `TRADES.PRICE` vs. `REFERENCE_PRICE_AT_ARRIVAL` (at `ORDERS.SUBMITTED_TS`) — did delay/market impact between order entry and execution cost the participant. The original draft used the arrival timestamp while claiming to measure execution quality — that was a wrong formula, not an open question; both metrics are now separately modeled and correctly labeled. Scoped per `VENUE_ID` (the reference price source is itself venue-dependent — some venues publish an NBBO-equivalent, others don't, and `TRADE_REFERENCE_PRICES`' columns are nullable for that reason, not an adaptor failure).

## RBAC — reused role shape, one new role, new object names

Same four functional roles as `Praman`, same boundary rationale, applied to the new schema, plus a fifth role the first draft omitted entirely:

- `ANALYST_READ` — `SELECT` on `RULE_CORPUS`/`APPROVED_OBLIGATIONS` (the view, not the base `OBLIGATION_MAP` table — Fix #6)/all core tables, `SELECT` on detector views including `WASH_DETECTION_COVERAGE` and `REPORT_TEMPLATE_COVERAGE` (Fix #28, v7 — without this grant `rule-interpret`/`assure-report` have no role that can run the completeness-companion query Fix #28 requires). No write access anywhere.
- `GOVERNANCE_WRITE` — `INSERT`-only (Fix #12 — the proposed→approved flip is a new row, not an `UPDATE`) on `OBLIGATION_MAP` and `OBLIGATION_RULE_CHUNKS`, `INSERT` on `RULE_CORPUS`, `SELECT` on the base `OBLIGATION_MAP` table (to see `proposed` rows for review, which `ANALYST_READ` cannot). Also `INSERT`+`SELECT` on `REPORT_TEMPLATES`/`REPORT_TEMPLATE_RULE_CHUNKS` (Fix #21, v6; `SELECT` added Fix #30, 2026-09-15 — an external review found this role could write these tables but never read its own rows back, unlike the `OBLIGATION_MAP` grant right next to it) — a report template is regulatory content, the same category as `RULE_CORPUS`, not raw market data.
- `AUDIT_INSERT` — `INSERT`-only on `AUDIT_LOG`, no `SELECT`.
- `OFFICER_SIGNOFF` — writes sign-off rows via a stored procedure (`SP_RECORD_SIGNOFF`, ported from `Praman`'s design), no direct table access.
- **`MARKET_DATA_INGEST`** (new, Fix #7 — the first draft had no write path for market data at all) — `INSERT`-only on `JURISDICTIONS`, `VENUES`, `INSTRUMENTS`, `MARKET_PARTICIPANTS`, `BENEFICIAL_OWNERS`, `ORDERS`, `TRADES`, `TRADE_CORRECTIONS`, `TRANSACTION_REPORTS`, `POSITIONS`, `TRADE_REFERENCE_PRICES`. Never `UPDATE`/`DELETE` on any of them — every lifecycle event on these tables (a `VENUES` status change, an `ORDERS` event, a `TRANSACTION_REPORTS` submission, a `POSITIONS` restatement) is an `INSERT` by design (Fixes #4, #10, #14, #16), so this role never needs update/delete and is never granted it. Also gains `SELECT` on `REPORT_TEMPLATES_CURRENT` (Fix #21, v6) — its first `SELECT` grant ever, needed to know which fields are required before generating a `TRANSACTION_REPORTS` payload; still no base-table read access anywhere. Can `CALL SP_RENDER_REPORT_PAYLOAD` (2026-09-15) — that procedure runs `EXECUTE AS OWNER` specifically because this role still has no `SELECT` on `TRADES` itself, same discipline as `SP_RECORD_SIGNOFF`.

No functional role holds `UPDATE`/`DELETE` on any `VIGIL.CORE` table as of the milestoning pass (Fix #18) — `OBLIGATION_MAP`'s `UPDATE` grant above was the last one.

`VIGIL.EVAL` (holding `INJECTED_CASES`/`EVAL_RESULTS`) is isolated the same way as `Praman.EVAL` — no functional role is ever granted anything on it. RBAC verification (the 22-check live-verification discipline `Praman` ran) is scheduled as a required step before this is considered done, not assumed correct because the grant scripts look right on paper.

## Governance gate

`OBLIGATION_MAP.STATUS` starts `proposed`; only a `GOVERNANCE_WRITE` session can write `approved` — and only after a schema-existence check on `SOURCE_TABLE`/`SOURCE_COLUMNS` passes (Fix #9; these are free text because SQL can't enforce an FK to a dynamic column name, but the approval workflow validates them against `INFORMATION_SCHEMA` rather than leaving that a silent drift risk). The flip itself is a **new row** with the same `OBLIGATION_ID` and a later `LOADED_AT`, not an `UPDATE` of the `proposed` row (Fix #12) — the full proposed/approved timeline is preserved, not overwritten. **The gate is now structural, not just a rule every future query author has to remember (Fix #6):** `APPROVED_OBLIGATIONS` is a view over the latest `LOADED_AT` row per obligation `WHERE STATUS = 'approved'`, and it's the only obligation-lookup target `ANALYST_READ`/the agent's obligation-lookup tool is granted — an unapproved (or not-yet-approved) obligation is invisible to the normal query path structurally, not merely supposed to be checked and skipped. This is the fix for the same real bug `Praman` hit once (a hardcoded default standing in for a missing lookup tool): building the structural constraint instead of trusting every future consumer to apply the discipline correctly, and testing it against a case where the check would actually fail (an unapproved obligation), not just the common case where it happens to pass.

## Agent and Skills

Four skills, parallel to `Praman`'s four but renamed for this domain — exact tool/orchestration split (single agent vs. multiple) to be decided during build, informed by `Praman`'s own finding that shared-resource stages (same Semantic Views/role) merge into one agent while stages needing bespoke multi-step orchestration don't fit a chat-agent tool-call model and stay as CLI skills:

- `surveillance-query` — live queries over trades/orders/positions (wash trading, spoofing candidates, exposure breaches). Parallel to `Praman`'s `signal-query`.
- `rule-interpret` — new exchange rule/circular → `OBLIGATION_MAP` gap analysis. Parallel to `circular-interpret`.
- `assure-report` — validate a draft transaction report / limit filing against rule text and obligation mapping before submission. Parallel to `assure-return`.
- `narrative-draft` — trace a confirmed surveillance finding to root cause via lineage, draft remediation/regulator narrative. Parallel to `narrative-draft` (same name, same thin-orchestration-over-native-lineage design).

**Design rule, added 2026-09-15 after three straight rounds of live adversarial testing proved it
the hard way (see NOTES.md's Q3/Q9 history):** an agent-honesty guarantee this project claims to
hold is implemented **structurally** — a schema/semantic-view fact the model can query directly
(e.g. `SV_DETECTOR_FINDINGS.COV.TOTAL_TRADE_VOLUME`, a real per-jurisdiction trade count sourced
straight from `TRADES`) — wherever a structural option exists. A natural-language instruction
alone (however carefully worded, and regardless of which of `instructions.orchestration` vs.
`instructions.response` it's placed in) is **never** treated as sufficient on its own for a
guarantee this project claims to hold — three consecutive instruction-wording rewrites changed
the agent's language without changing its tool-selection behavior, and only a schema change
reliably held. `cortex_project/coco_task_verify_agent_routing.md` is a **living regression suite**
under this rule, not a one-off handoff artifact: re-run it after any change to
`vigil_agent.sql`'s tools/instructions, and append at least one new adversarial question for
every new tool or Semantic View added, rather than letting the original 9 (now 11) questions
quietly stop being representative of what the agent can actually be asked.

## Synthetic data — config-driven, with a measurable agnosticism criterion (Fix #9)

`Praman`'s generator reconciled bottom-up to one real disclosed PDF (HDFC's Pillar 3). No equivalent single document exists for trade surveillance, so this generator is parameterized by a `JURISDICTION_CONFIG` (jurisdiction, its full verified venue list, currency, trading calendar, instrument universe, participant count per venue) instead. Japan's config is the first, seeded from the 6 confirmed active venues (`XTKS`/`XOSE`/`TOCOM`/`JPNX`/`ODX`/`ODXST`) plus 2 confirmed-discontinued venues (`CBOJ`/`CBOJBIDS`, `DISCONTINUED_AT = '2025-08-29'`) — the generator must produce historical `ORDERS`/`TRADES` for the discontinued pair only with timestamps before their `DISCONTINUED_AT`, proving the date-bounded design actually works rather than just being documented. Not a single venue standing in for the whole jurisdiction, since the whole point of the `VENUE_ID` split is that a realistic Japan dataset has orders/trades spread across all 8 venues, with wash-trading/best-execution cases that specifically span venues. `US` and `EU` are the second and third configs for the agnosticism proof (`generator/jurisdiction_config.py`, built and loaded 2026-09-15) — both live-verified the same way Japan's was, not a bulk copy of a secondary source. `US`: 7 major national securities exchanges (NYSE, Nasdaq, NYSE Arca, Cboe BZX, Cboe EDGX, IEX, MEMX) live-verified against the SEC's own current Section 6(a)-registered exchange list (29 total; the rest are mostly single-purpose options exchanges), plus FINRA's Alternative Display Facility as a real OTC reporting venue — 8 venues total. `EU`: "EU" is not one exchange, so one concrete, real, currently-operating member-state market was picked instead — Germany/Deutsche Börse Group (Xetra, the Frankfurt Stock Exchange floor, Tradegate Exchange, Börse Stuttgart), live-verified via Deutsche Börse's own site — 4 venues. Both loaded via `scripts/load_us_eu_configs.py`; every detector view now returns real, non-trivial findings for both (wash trading, spoofing, position limits, reporting timeliness, best-execution slippage all produce real non-zero numbers — see NOTES.md 2026-09-15 for exact figures), not just structurally-possible zero rows.

**"Market-agnostic" is now a measurable claim, not "behave identically" left unspecified:** running the generator against both configs must produce (a) 100% referential integrity across every FK, (b) every seeded `VENUE_ID` represented in at least one `ORDERS`/`TRADES` row, and (c) each detector's trigger rate falling within a documented expected band for that config's synthetic distribution — not literally equal absolute counts across two differently-sized configs, since "agnostic" means the mechanism behaves the same way, not that two different-sized datasets produce equal numbers.

## What's explicitly deferred

Real regulator/exchange document sourcing (a `Praman`-style `data-sources.md` equivalent) for Japan's actual FSA/SESC/JPX rule text was completed 2026-09-14 for the five detector-backed obligations — real citations from the FSA's own FIEA translation (Art. 159(1)(i)/159(2)(i)/40-2) and Osaka Exchange's own Operational Procedures document (Section IV/III(1-1)), loaded into `RULE_CORPUS`/`OBLIGATION_MAP`/`OBLIGATION_RULE_CHUNKS` via a real `INFORMATION_SCHEMA`-validated approval gate (`SP_APPROVE_OBLIGATION`) — see NOTES.md and `sql/governance/01_rule_corpus_and_obligations_seed.sql`. `REPORT_TEMPLATE_RULE_CHUNKS` now has 65 real field-level citations for EU `transaction_report` (RTS 22 Annex I Table 2, `sql/governance/03_eu_report_template_rts22_seed.sql`, 2026-09-15) and 138 for a new JP report type, `otc_derivative_transaction_report` (`sql/governance/06_jp_otc_derivatives_report_template_seed.sql`, 2026-09-15) — sourced from the FSA's own "Guidelines for Creating, Recordkeeping and Reporting of Transaction Information" (Cabinet Office Order No. 48 of 2012, Art. 4(1); FIEA Art. 156-63~65), a real, numbered field list Japan adopted from the internationally harmonized CDE (Critical Data Elements) OTC-derivatives-reporting standard. Found only on a fourth pass, after three real, thorough searches (this session's two plus a fresh JPX Business/Trading Participant Regulations check) had all correctly concluded nothing existed for *equity* transaction reporting — the fourth pass searched OTC derivatives specifically, a different regulatory track, and found it. Deliberately a separate `REPORT_TYPE` from JP's existing 4-field `transaction_report` (equity-shaped, matching `JAPAN_CONFIG`'s equity-only instrument universe) rather than folded in — mixing the two would misattribute a derivatives-specific citation to an equity report. Originally only 3 of 138 fields resolved to a real column; a scoped MVP pass (2026-09-15, `sql/ddl/10_otc_derivatives.sql`, `sql/governance/07_jp_otc_derivatives_field_mapping_gap8_mvp.sql`/`08_jp_otc_derivatives_price_field_precision_fix.sql`) built a real fixed-for-floating interest-rate swap model — `MARKET_PARTICIPANTS.LEI`, `DERIVATIVE_PRODUCT_ATTRIBUTES` (product-level: UPI, asset class, contract type, underlying — real, BOJ-administered TONA), `DERIVATIVE_TRADE_DETAILS` (trade-level: UTI, notional, fixed rate, day count, payment frequency, effective/maturity dates), and a real venue, DDRJ (DTCC Data Repository (Japan) K.K., the FSA-designated Trade Repository these transactions are actually reported to under the same FIEA Art. 156-63/64/65 this citation cites) — raising coverage to 23/138 (16.7%). Deliberately still out of scope: valuation/margin/collateral (fields 39-63) and every option/CDS/package-specific field, which need a real mark-to-market/collateral-posting model this pass didn't build. A real, separate, pre-existing platform gap was found and partially addressed along the way: a bare `NUMBER` column defaults to `NUMBER(38,0)` in Snowflake, so `TRADES.PRICE`/`VOLUME` and every other bare-`NUMBER` column across the whole schema silently truncate to integers — fixed for the two new derivative-specific columns (explicit `NUMBER(9,6)`/`NUMBER(20,2)`) and REPORT_TEMPLATES' Price/Price-currency fields re-pointed to them, but **not** fixed retroactively for `TRADES`/`ORDERS`/`TRADE_REFERENCE_PRICES`/`POSITIONS` platform-wide — that remains open, flagged here rather than silently repeated or silently fixed without a decision on restating historical data. The remaining 115 fields (margin/collateral/valuation/option/package) are real, required, and genuinely unsourceable today without that further model. Corporate-actions handling for `POSITIONS` (Fix #4) is now built (`CORPORATE_ACTIONS`/`POSITIONS_ADJUSTED`, 2026-09-15). The full per-regulator XML/fixed-width report-rendering adaptor has a first real version too (`SP_RENDER_REPORT_PAYLOAD`/`SP_RENDER_REPORT_PAYLOAD_XML`, multi-table-aware) but is not a claim of full per-regulator schema conformance. `US`/`EU` venue lists are now live-verified and loaded (see the paragraph above) — "market-agnostic" is proven across all three jurisdictions now, not just Japan.
